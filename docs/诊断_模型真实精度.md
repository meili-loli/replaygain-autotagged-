# 诊断报告：模型的真实精度是 0.79 dB，不是 0.383

日期：2026-10-16
数据：`delta_gain.csv` 909 首，`feat_cache/` 909 个 npz，`handcraft_cache_42d_aug05.pkl`

## 一、结论（一句话）

**`eval_out/group_summary.csv` 里的 MAE 0.383 是测错的数字。**
真实精度（生产环境会拿到的）是 **≈ 0.79 dB**，比报告值差一倍。

三种互相独立的评估协议给出同一个答案：

| 评估协议 | MAE | 说明 |
|---|---:|---|
| GroupKFold（原始+增强锁同折） | **0.788** | 干净协议 |
| 朴素留出 700训/209测（无增强） | **0.787** | 最无争议 |
| GroupKFold + 无增强 | **0.784** | 干净协议 |
| ~~朴素 KFold（现状）~~ | ~~0.383~~ | **有泄漏，作废** |

## 二、0.383 是怎么来的 —— 两个叠加的错误

### 错误 1：增强样本泄漏（-0.42 dB 的假象）

`train_eval_export.py` 的 `build_cache_from_csv` 把原始样本和增强样本
**堆叠成同一个 1818 行的数组**：

```python
X = np.vstack([X_orig, X_aug])
y = np.concatenate([y_orig, y_aug])
```

然后 `run_oof` 用普通 `KFold` 随机切分。于是**同一首歌 `A` 和它的增强副本 `A'`
经常被分到不同的折** —— `A'` 在训练集里时，模型等于"见过"了 `A`。

`A` 与 `A'` 只差一个 0.5 dB 的整体增益，标签也正好差 0.5 dB，
模型只要在两个点之间插值就能几乎完美命中验证样本。

改成 `GroupKFold`（同一首歌的两行锁在同一折）：

| | MAE |
|---|---:|
| 朴素 KFold（有泄漏） | 0.519 |
| GroupKFold（无泄漏） | **0.940** |

**泄漏值 = 0.42 dB。**

### 错误 2：报的是 5 个模型的平均，不是模型本身

`per_seed_sample.csv` 里每首歌有 5 行（5 个不同折划分下的 5 个模型）。
`group_summary.csv` 的 0.383 是**这 5 个预测取平均之后**的误差。

但 `model_dir/meta.json` 里没有 `n_ensemble` 键，`load_models()` 默认
`n_ensemble = 1` —— **实际部署的是单个模型**。

| | MAE |
|---|---:|
| 单模型（= 生产环境实际） | 0.517 |
| 5 模型平均（= 报告里的 0.383） | 0.379 |

这 0.138 的差额**拿不到**：那 5 个模型各自训练在不同的 80% 子集上，
生产环境只有一份数据。

### 顺带发现：`--n-ensemble` 是空操作

```python
lgb.LGBMRegressor(n_estimators=300, learning_rate=0.05, num_leaves=31,
                  min_child_samples=10, random_state=seed, ...)
```

没有 `bagging_fraction` / `feature_fraction` 时，LightGBM 是**确定性**的。
实测 `seed=0` 与 `seed=1` 的预测**逐位相同**（最大差异 0.0000000000）。

所以 `--n-ensemble 5` 会训练出 5 个一模一样的模型，收益恒为 0。
这就是交接文档里"P2 预期收益 0.01~0.03 dB"的真实原因。

## 三、更大的发现：双专家 + 门控架构是**负收益**

干净协议（GroupKFold）下的方案排行榜：

| 方案 | MAE |
|---|---:|
| **单 LGB 回归（42 维直接回归）** | **0.788** |
| Ridge 回归（42 维） | 0.820 |
| 双专家 + 门控，软路由 | 0.881 |
| 双专家 + 门控，硬阈值 | 0.940 |

**连最简单的 Ridge 线性回归都比现有的双专家+门控好。**
架构本身拖累了 0.15 dB。

原因很可能是设计上的空洞：

```python
LOW_THR = -10.0    # low 专家训练条件: y < -10
A_THR   = -9.0     # a   专家训练条件: y >= -9
```

`-10 <= y < -9` 这个区间**两个专家都没训过**，但推理时总得有一个专家来预测它。
报告里 `-11 ~ -9` 分组 MAE 最差（0.432）正是这个洞。

另外门控的监督信号来自内层 OOF 的专家预测 —— 数据少时专家本身就差，
`label = 1 if |y-low|-|y-a| > 0` 这个标签就是噪声，门控学不出东西。

### 增强样本也没有用

| 训练数据 | MAE |
|---|---:|
| 只用 909 首原始样本 | 0.7844 |
| 909 + 909 增强 | 0.7877 |

增强不但没收益，还是泄漏的来源。**建议直接删掉。**

### 超参几乎没有调优空间

`num_leaves` 7/15/31/63、`n_estimators` 150~1200、`min_child_samples` 5/20/40
扫下来全部落在 **0.782 ~ 0.796**，是个平台。

## 四、那么瓶颈到底在哪？

### 不是数据量

单 LGB 的学习曲线（纯留出，无增强）：

| 训练首数 | MAE |
|---:|---:|
| 200 | 0.917 |
| 300 | 0.869 |
| 450 | 0.861 |
| 600 | 0.833 |
| 750 | 0.784 |
| 909 | 0.787 |

拟合 `MAE = 0.685 + 3.32/√n`：

- 翻倍到 1800 首 → 0.763（只赚 0.03）
- 四倍到 3600 首 → 0.740（只赚 0.05）
- **渐近下限 0.685**

**多标歌的收益已经很小了。**

### 也不是（全部）标签噪声

渐近下限 0.685 意味着"就算数据无穷多，MAE 也停在 0.685"。
如果把 0.685 全算作标签噪声，反推 σ_n = 0.685 / 0.798 ≈ **0.86 dB**
—— 比用户说的"±0.5 散布"大得多，不太可能。

所以**主要是 42 维特征带的信息不够**，不是模型不行、不是数据不够、也不全是标签噪声。

### 一个没验证成的方向：专辑先验

用户是**按专辑标注**的（`annotate_gain.py --input <专辑目录>`），
理论上同专辑的歌 delta_gain 应该接近。但实测：

- `delta_gain.csv` 只有 `file`（纯文件名）+ `delta_gain` 两列，专辑信息丢失
- 按所在目录分组，30 个"目录"里有一个装了 284 首、一个 182 首
  —— 目录结构根本不等于专辑
- 用"同目录其他歌的均值"预测，MAE = 1.42，比模型差

**结论：现有 CSV 里没有可用的专辑结构。**
如果以后标注时把专辑/艺人信息保留下来，专辑先验很可能是个大特征。

## 五、建议

### 立刻做（按收益排序）

1. **修正评估协议** —— `run_oof` 改用 `GroupKFold`，`groups` 设为歌的原始编号。
   否则所有后续实验的读数都不可信。
2. **换回单 LGB 回归** —— 比双专家+门控好 0.15 dB，代码还短得多。
3. **删掉增强样本** —— 无收益，且是泄漏源。删了还能省一半训练时间。
4. **做一次 test-retest 实测标签噪声** —— 这是唯一能给出"还有多少空间"的实验：
   挑 60~80 首已经标过的歌，**不显示旧值**重标一遍，算 MAE(旧, 新)。
   - 若 ≈ 0.35~0.40 → 标签噪声就是主要下限，模型已接近天花板
   - 若 ≈ 0.15~0.20 → 模型还有很大空间，值得继续做特征

### 中期

5. **加特征，而不是调模型**。当前 42 维明显不够。优先考虑：
   - 专辑/艺人的目标响度先验（需要标注时保留元数据）
   - 更细的响度分布（短时窗 LUFS 分位数、gating 前后差）
   - 频谱倾斜 / 音色描述子（和用户的 EQ 曲线相关）
6. **保底改进**：软路由。单模型下 `pred = low + w·(a-low)`，
   `w = clip((prob-(τ-δ))/(2δ), 0, 1)`，δ=0.2：
   0.517 → 0.481。**但换回单 LGB 后这个问题自动消失。**

### 不要再做

- 不要再加大极端组权重 / 调 τ（都是在泄漏协议上调出来的）
- 不要再动 `--n-ensemble`（在修好 `random_state` 之前完全无效）
- 不要加深度学习（909 首，且渐近下限已到 0.685）

## 八、补充：按「尾部指标」重新评估（2026-10-16 追加）

用户明确表示**不关心 MAE，关心的是最大误差和 >2 dB 的样本数**。
按尾部指标重测（干净协议，15 个折 × 909 首）：

| 方案 | MAE | p95 | p99 | max | >2dB 首数(/909) |
|---|---:|---:|---:|---:|---:|
| 现状（双专家+门控，硬路由） | 0.940 | 2.51 | 3.57 | 5.94 | **95** |
| 单 LGB + 极端区加权 | 0.784 | 2.12 | 3.11 | 4.84 | **57** |
| 单 LGB | 0.788 | 2.17 | 3.03 | 4.88 | **60** |
| 单 LGB × 5 真集成 | 0.772 | 2.11 | 3.08 | 4.84 | **55** |

**换掉双专家架构，>2 dB 的歌曲数直接从 95 首砍到 60 首（-37%），max 从 5.94 降到 4.88。**
这个结论在 MAE 和尾部指标下一致 —— 架构本身是负收益。

### 误差分布不是高斯的

| 阈值 | 实测 | 高斯预期 |
|---|---:|---:|
| \|err\|>1 | 29.2% | 31.1% |
| \|err\|>2 | 6.6% | 4.3% |
| \|err\|>3 | 1.1% | **0.24%** |

>3 dB 的误差是高斯预期的 **4.5 倍** —— 尾部有额外的来源。

### 尾部误差里，约 3/4 是标注打滑

`find_label_outliers.py` 用「残差大 且 自己标签偏离特征邻域中位数」筛选：
909 首里 59 首可疑。

典型例子（邻居标签紧紧聚在一起，就它自己飘出去）：

```
y=-8.00  pred=-10.50  邻域中位数=-10.50  邻居=[-9.5 -10.5 -10.0 -11.5 -9.5]
y=-8.00  pred=-10.16  邻域中位数=-10.25  邻居=[-10.0 -10.0 -11.0 -10.5 -10.0]
y=-5.00  pred= -8.35  邻域中位数= -8.25  邻居=[-8.5 -8.5 -10.0 -8.0 -8.0]
```

**检测器有效性（注入已知噪声验证，`diag_detector_validation.py`）：**

| 场景 | 标记数 | Top59 命中注入 | 相对随机 |
|---|---:|---:|---:|
| 对照组（不注入） | 56 | — | 基准 |
| 注入 60 首 ±2~3.5 dB | 92~99 | 34~37 / 60 | **约 9 倍** |
| 注入 60 首 ±1.5~2.5 dB | 76~77 | 20~22 / 60 | 约 5 倍 |

预期命中率约 60%，**小于 2 dB 的打滑基本检测不出来**。

### 人的噪声决定了天花板

对**已有标签**测出来的误差恒等于：

```
OOF 误差² = 模型真实误差² + 标签噪声²
```

即使模型完美，测出来的 MAE 也只能到 `0.798 × σ_噪声`。
若 σ_噪声 = 0.5，则不论怎么优化，MAE 都不会低于 ~0.40。

### 顺带修掉的两个隐藏 bug

**1. 文件名里的特殊字符会崩掉整个推理进程**

Windows 控制台默认 GBK。文件名含 `♯`(U+266F) 之类的字符时，
`print(f'  [WATCH] ... {os.path.basename(fp)}')` 会抛 `UnicodeEncodeError`，
**整个多进程任务直接死掉**（不是跳过那一首）。

```python
try:
    sys.stdout.reconfigure(errors='replace')   # 改成替换而不是抛异常
except Exception:
    pass
```

已加到 `predict_and_tag.py` 和 `train_eval_export.py`。

**2. `--workers 16` 会把内存打爆**

实测：物理内存 31.2 GB，可用 9.8 GB（其他程序占了 68%）。
16 个 worker 同时跑 librosa 的 HPSS + 长音频解码会 `MemoryError`，
全库 1086 个文件里挂了 11 个（都是 24bit/96kHz 的 Hi-Res 文件）。

`--workers` 不指定时的默认值已从「全部核心（本机 32）」改成
`min(cpu_count, 8)`。**手动指定时建议不要超过 8。**

### 试过但没用的：后处理校准（负面结果，别再试了）

看 OOF 残差，极端组 `y >= -7` 有明显的正偏置：

| 分组 | n | 偏置 (y-pred) | t 值 |
|---|---:|---:|---:|
| y < -11 | 245 | -0.582 | -10.4 |
| -11 ~ -9 | 384 | -0.051 | -1.2 |
| -9 ~ -7 | 175 | +0.472 | +6.6 |
| **y >= -7** | **61** | **+1.141** | **+8.1** |

而且剔除可疑标签后偏置仍有 +0.73（t=6.9），**不是标签噪声造成的**。

看起来像「模型在极端区回归均值」，于是试了三种校准：

| 方法 | MAE | >2dB | 结论 |
|---|---:|---:|---|
| 不校准（基线） | 0.762 | 53 | — |
| 等距回归 Isotonic（5折） | 0.793 | 52 | 更差 |
| 全局线性 a·p+b（5折） | 0.762 | 52 | 无变化 |
| 「预测值 >= T 的子集整体平移」（10 seed 均值） | 0.764 | 52 | **无变化** |

> **踩坑记录**：分组平移一开始看着很有效（MAE 0.736、>2dB 53→44），
> 但那是用「**标签** y >= -7」挑子集挑出来的 —— 推理时拿不到标签。
> 改成用「**预测值** >= T」挑，10 个 seed 平均后收益完全消失。
> 单 seed 的漂亮数字是折划分的运气。**任何后处理校准都要多 seed 验证。**

结论：**八种后处理全都不泛化。模型的上限就是模型本身。**
